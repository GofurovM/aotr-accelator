# Engineering notes — read this first

This is the project's memory. It is written for a developer, or an AI assistant such as Claude, who picks the work
up cold. Start here, then read the header comment of the `.inc` file you are about to touch. Every part explains
its own why, its proof and its addresses at the top of its file.

## Ground rules (never break these)

1. **Multiplayer first.** The logic, its timing and its random numbers must come out bit-for-bit as without the
   DLL; players without it must stay in sync. The logic rate, frame cap and game speed are never touched (upstream's
   60 fps tween and LogicHz features exist in the tree but are off). A part that answers a *logic* question
   faster must prove itself (see "Self-proof").
2. **No broken pictures.** A part that could change what is drawn is not shipped. Two such parts were removed
   because players saw the effect: half-rate shadow maps (shadows flickered) and in-between frames.
3. **game.dat and the game folder are never modified on disk.** Everything is done in memory, after injection by
   `aotr_start.exe`. The AotR launcher checks the files.
4. **AOTR only.** The starter injects only into a game.dat that belongs to the chosen AOTR install.
5. **Fix, do not just remove.** When a part misbehaves, find the cause. Remove it only with a measured reason.
6. **Open-BFME-2, the EA Generals source and OpenSAGE are maps only.** Names, structure and the idea of an
   algorithm may come from them, never code: they are GPL/LGPL and this DLL is MIT. All code here is the
   project's own plus upstream (MIT).

## The target and how parts are anchored

- **Build:** RotWK 2.02 as AOTR ships it, the "delayfix" game.dat. `.text` FNV-1a hash `0xDE0F8163`; the stock
  2.02 hash is `0x5ED63115`; AOTR 10's game.dat is `0x66C9806A` (the delayfix build plus 15 bytes changed in 6
  places of the AI's target search: 0x7019FD, 0x701ACB, 0x701B23, 0x813112, 0x9D6360, 0x9D6373).
  `initThread` in `aotr_accel.cpp` hashes `.text` and sets `g_engineHooks` for a known build.
- **A newer AOTR game.dat** with the same header (stamp `460DA09E`, size `AD4000`, checksum `ADC2F6`, entry
  `63D082`) gets the address-anchored parts too, if every anchor still holds the verified bytes.
  - The anchors are in `aotr_anchors.inc`: 549 addresses named in the source, 16 bytes each, generated by
    `tools/gen_anchors.py` from the delayfix game.dat.
  - Otherwise those parts stay off, and the status light is red ("unknown game.dat build").
  - After adding a new address to the source, run the tool again.
- **Portable parts** run on any build: the render thread, texture workers, fast CRT and file layer. They hook by
  import name or by the Direct3D vtable.
- **Address-anchored parts** compare the exact bytes they patch first, and stay off if anything differs.
- **Key globals:** TheGameLogic `[0xDE412C]` (`+0x40` logic frame counter, `+0x110` game mode: 1 LAN, 5 online,
  9 shell map); TheTacticalView `[0xDE447C]`; ThePlayerList `0xDE4928`; TheFXParticleSystemManager `0xDE3744`.
- **Engine loop:** the frame dispatcher `0x6329B0` (AOTR's own patch calls update(1) and update(2) in one render
  frame, so a 5 Hz logic step is 5 render frames); `GameLogic::update(n)` `0x62E4E8`; the frame limiter `0x63A1DC`.

## Threads and data flow

- **Game thread:** the engine's main thread, which runs logic and client. The DLL gives it a physical core of its
  own (`aotr_sched.inc`, `CORES_OFF`) and replaces the limiter's spin with a sleep until 2 ms before the frame end
  (same end time).
- **Render worker** (`aotr_rt.inc`, generated hooks in `aotr_rt_gen.inc` from `gen_rt_hooks.py`; DXVK only):
  - Every D3D9 and ID3DXEffect call of the game thread is recorded in order and executed on the worker.
  - A call that must return data waits for the queue: only for the records that name that object where that is
    provably enough (buffer "fresh copy" locks, self-checked), else for the whole queue.
  - Freeze guard: a 250 ms wait in play (2500 ms while loading) steps the worker aside for 10 s, at most 3 retries.
  - On Windows' own d3d9 the worker is not used (it rewrites the device vtable under us).
- **Texture workers** (`aotr_texjobs.inc`): D3DX decode, mip chains and DXT compression run on up to 6 threads.
  Results are uploaded through the render queue in order. The first 24 results are compared with D3DX on a real
  texture; one difference turns this off for the session.
- **Ground patch helpers** (`aotr_terrain.inc`): each new 512×512 ground patch texture is built by the game
  thread and 5 helpers. The first 24 are also built the engine's way and compared.
- **File threads** (`aotr_fdbuf.inc`, `aotr_filewarm.inc`, `aotr_preload.inc`) read into the Windows file cache at
  background priority, and stand back whenever the game reads.
- **Report thread** (`aotrProdReport30`): every 30 s it saves the learned list and moves new threads off the game's
  core. Its log lines appear only in the diagnostics build.

**Self-proof.** Every logic-side part keeps the engine's original reachable through a trampoline. For the first
N answers of a session it runs both and returns the *original's* answer. One difference turns the part off for the
rest of the session and logs a line containing "for the rest of this session". The diagnostics build keeps
re-checking 1 in 64 (or a similar sample) afterwards (`AOTR_STEADY` in `aotr_accel.cpp`). A 2.5-hour multiplayer
session with that sampling: 208 million checks, 0 differences.

**Processor levels** (laptops). The DLL measures the processor's real speed every 2 s. If it falls under 35% three
times in a minute (a laptop's heat or charger limit), it asks `aotr_start.exe`, through `aotr_throttle.txt`, to cap
the highest clock at 150 / 130 / 115% of base, and then to turn Turbo off. If fps falls, it goes back to the best
level. Everything is restored when the game closes.

**The status light's colours** (`bdgState` in `aotr_badge.inc`):
- **Red:** the build is not known (`g_engineHooks` 0); or the render thread was tried and not installed (Direct3D
  is Windows' own, not DXVK); or the freeze guard used up its retries.
- **Yellow:** any log line written with one of the problem phrases (`logIsProblem` in `aotr_accel.cpp`): "rest of
  this session", "for this session", "SELF-CHECK", "MISMATCH", "FREEZE GUARD", "SAFE MODE". Keep those phrases
  for problem lines only.
- **Green:** none of the above.

**The starter** (`aotr_start.cpp` → `AOTR_ACCELERATOR.exe`; a GUI program, `asInvoker`):
- **From the package folder** it re-launches itself elevated with `--install`, then:
  - copies itself, the DLL and the guides to `%ProgramData%\AOTR Accelerator`;
  - registers the Task Scheduler task "AOTR Accelerator" (logon trigger, `HighestAvailable`, no battery limits,
    `--background`);
  - makes the desktop shortcut and starts the resident through the task.
- **The installed copy** is the resident: one per user (a mutex), with a hidden window in the notification area.
  - The task starts it at logon. The shortcut, running without rights, finds its window and posts
    `WM_AOTR_LAUNCH`; `ChangeWindowMessageFilterEx` lets that one message through. If no copy is running, it
    starts the task, so there is no Windows prompt.
  - With "Start with Windows" off, the task stays without its trigger.
  - The monitor thread polls for the AotR launcher (learns the AOTR folder from it, opens the files ahead once)
    and for game.dat. It injects, raises the power plan while the game runs, and reads `aotr_status.txt` every 2 s.
  - The ring is red if no status file with the game's pid appears within 60 s of the injection.
- **From the source tree's `out\`** (PLAY.bat) it installs nothing. It asks an installed resident to step aside,
  and ends 20 s after the game closes.

## Measured: where the time goes in a big battle

Measured on a laptop (Intel + GeForce, DXVK) at the 30 fps cap; a frame has 33 ms.
- **Logic:** 15–21 ms per frame once the 5 Hz step is spread over its frames.
  - AI target search is the biggest share: `findClosestEnemy`, the whole-map query `0xA39420` via `0x700B00`,
    about 1 ms each and about 2000 every 30 s.
- **Client and drawing:** 12 ms in calm play, 25–35 ms in the biggest fights.
  - `UpdateShadowMap` `0x47D5C9` 3–8 ms; RenderViews 6–13 ms; particle update 4–8 ms; the rest 9–14 ms.
- **Together:** 18–22 fps in the heaviest moments, on one thread. Neither half can be split further without
  changing results (logic) or pictures (drawing).

**Hitches** in play come from first appearances: a unit or spell whose models and textures were never loaded.
They read files, decode textures and build shadow meshes. The file cache preload, texture workers and shadow
neighbour fix cut these down. A cold PC (just restarted) has more of them for the first minutes, because the
virus scanner looks at each file once.

**32-bit address space.** The game is Large Address Aware: 4 GB on 64-bit Windows. AOTR alone uses 2.0–2.5 GB.
In v65 the engine-side preload pushed it to 3.6 GB and the pictures broke: stretched trees and odd spell effects.
Since then nothing is loaded *into* the game ahead of time, only into the Windows file cache.

## Tried and rejected (with the reason)

- **Engine-side preload** (`ThingTemplate::GetAssetList` `0x73E909` + `AddKeys` `0xA32CC0` on the loading screen and
  in small pieces during play). It loaded 1000–3400 templates ahead. Broken pictures in spells (Army of the Dead,
  the spider forest, missing Balrog rocks) appeared with it, and the engine itself never takes this path
  (`GlobalData+0x1110`). Off since v67; `PRELOAD2_ON` turns it on for experiments.
- **Half-rate shadow map** (`aotr_shadowhalf.inc`, removed). Shadows flickered when the camera moved, because the
  shadow picture is fitted to the camera.
- **Upstream's in-between frames, merged draws, frame cap / logic rate, call de-dupe, texture disk cache, rpmalloc,
  preshader cache.** They either change pictures or timing (multiplayer), were measured slower, or gave no gain.
  The code of the ones still referenced stays in the tree, but none is installed.
- **Reordering the AI whole-map query filters.** All the filters behind `0x700B00` call virtual functions or
  write memory (static check), so their order is part of the simulation. Only a prefetch was added
  (`aotr_partfast.inc`).
- **Pose warm-up** (skeleton updates on workers). Exact, but measured with no gain. `AOTR_POSEWARM2=1` turns it
  on for a measurement.
- **Particle list prefetch** (`aotr_pswarm.inc`). No gain. `PSWARM_ON` turns it on.

## Open issues

- **Long upward shapes at full graphics (v74 test, AOTR 10, single player, 18 min).** Seen around buildings under
  construction and upward light effects. Not pxpar (it spread nothing in that game) and not memory (2.56 GB, the
  largest free block never below 1.4 GB). First suspect: the logic slicer's pauses *inside* a module list - a frame
  can then draw an object whose modules ran only in part (a construction's rise or an effect's attachment set by a
  later module of the same step). The vanilla engine draws mid-list only at list 0's half. Test: `SLICER_OFF`; then
  `VANILLA` (to rule out AOTR 10 itself).
  - **v76 glitch hunt (diagnostics build):** in play the slicer is off every second 3 minutes and the particle
    spread every second 5 minutes (`ghTick` in aotr_accel.cpp). The player presses the right Ctrl when a glitch is
    on the screen; each `MARKER` line names the state, and a `glitch-hunt:` line every 30 s counts the markers per
    state with the minutes spent in it. Markers that all fall in one state name the cause in a single game.

- **Rare broken geometry after a long session on one PC.** It was seen once, in match 5 of a 2.5-hour session
  (v68).
  - The other player, in the same matches, did not see it. Memory was 2.46 GB of 4; every self-check was clean.
    Nothing in the log points to a part.
  - Suspects, in the order to try with the switch files:
    1. the logic slicer (`SLICER_OFF`): frames are drawn *between* module updates of one step, so a freshly
       spawned object can be drawn before the rest of its step ran;
    2. the radar hooks (`RADARHOOKS_OFF`);
    3. terrain-keep (`TERRAINKEEP_OFF`).
  - Also collect DXVK's own log (`rotwk\game_d3d9.log`); look for memory allocation failures.
  - v71: the DLL lets go of its own short-cut tables after every fifth match, and the starter suggests a restart
    after 2.5 hours. Both act on the "long session" pattern without knowing its cause.
- **Where the drawing time goes at full graphics (v74 sampler, 50 a second):** UpdateShadowMap 4.7 ms a frame,
  RenderViews 5.1, the rest of the client step 4.9, RenderUI 1.0 (slowest tenth 5.5 / 6.1 / 9.1 / 1.2). The
  shadow map is the scene rendered again from the light (0x47D5C9 > WW3D render 0x517C60). About two thirds of all
  client samples are under the W3D render-object functions (0x59C080 / 0x5A4DD0, virtual) - the engine's own
  serial renderer, with no single hot spot (the top leaf is ~2.5%). Batching compares lighting environments of
  neighbours in a sorted list (0x573BEB > 0x549430 > 0x53F3B0): linear, ~5% of the client. Particle draw
  (module 6, 0x961DFC) fills global arrays per system: ~6%.
- **The heaviest fights dip to 18–22 fps.** The remaining cost is the engine's single-threaded logic plus drawing.
  The next exact candidates are inside drawing: the shadow pass and particle update, not the logic.

## Particle update on several cores (v74, `aotr_pxpar.inc`; addresses from AOTR 10's game.dat)

Client-only work (pictures): no multiplayer risk either way. The file's header comment holds the whole argument;
this is the map.

**The engine's order:** `ParticleSystemManager::update` (0x5F5123, a virtual: vtables 0xBF7A28 / 0xBDAC38) walks
its system list (+0x4C; node+8 = the system). Skip test at 0x5F51D9: `[sys+0x98] == 0` and the flag at
`[ebp-0xD]` (0x5F51A8: `[[0xDE4388]+0xC8] && ![[0xDE412C]+0x125]`). Each system: vtable slot 4 = 0x5FA2CE:
1. early returns only at 0x5FA314 (global `[[0xDE4364]+0x9AF] == 0`) and 0x5FA33D (delay counter sys+0x120);
2. follows its drawable / object, builds its transform (+0xEC..);
3. emits (0x5F3CCF, may evict any particle: 0x5F3F18 picks the oldest by priority list, not by state);
4. its own modules: chain +0x1AC .. +0x1C8, then a vector at +0x1CC (0x5F9F6D > ... > 0x5F3A19);
5. 0x5F332E: the container (+0xA4) slot 0x28, then slot 0x1C (count) decides if the system lives on.

**The particle (0xC0 bytes, vtable 0xBF7B70):** handle to its system at +0x3C {target, +0x40, +0x44}; a system
that follows it at +0x78 {+0x7C, +0x80}; render object +0x8C (model particles); container list next +0x64,
prev +0x68, in-container flag +0x74; priority list +0x6C / +0x70, flag +0x75; life +0x54. Modules: +0x94
C32A64 (0xB0 bytes), +0x98 C329B0 (0x5C), +0x9C C32BD0 (0x38), +0xA0 C32B18 physics (0x18: +0x10 drag,
+0x14 follows a drawable, +0x15 follows the system's position), then +0xAC (C32C80, drawable-attached), then a
vector [+0xB0, +0xB4). Each module points back to its particle at +4. Deleting: only through slot 0 (0x5FBACA >
0x5FB7FC > base 0x5F42D9, which leaves the container, the manager's priority list and both handles).

**`Particle::update` (0x5FA0E6) call tree:** 31 functions (kPxCode in the file, one FNV hash checked at start-up,
the same bytes in delayfix and AOTR 10). No global write, no lock, no random. The physics module links a stack
handle to the particle's system (0x44C4BE / 0x44C43F) and unlinks it (0x44C465): the system's handle list is the
only shared write, so a system's particles never go to two threads. With a drift module at sys+0x1B8 the physics
reads its getters (slots 4 / 5) - such particles stay with the engine.

**What v74 does:** picks at the loop's start (0x5F51BC), updates the picked ones on `tpAutoHelpers()` (max 6)
helpers + the game thread, keeps alive/dead in a stamped hash table; the replaced container update (pxCont) uses
the kept result at the engine's own moment and deletes there. The particle destructor hook forgets results.
Self-checks: copies of 8 picked particles every 16th frame compared just before the engine updates them; results
never used counted; helper exceptions. Any failure: off for the session, yellow light.

**v75 - the v74 census, and what it opened:** in the v74 test (AOTR 10, full graphics) pxpar spread nothing: of the
particles counted, 93% had a drift module at sys+0x1B8 and 20% a system module not yet verified. Read since:
- the drift module is C32AC8 on every system that has one: no update (`ret`), slot 4 `fld [ecx+2Ch]`, slot 5
  `lea eax,[ecx+20h]` - the physics module reads two of its constant fields. Allowed; its first 0x30 bytes (of 0x40)
  joined the check copies.
- system modules in use (+0x1AC..+0x1C8): all `ret` except C331B4 (0x9686C0, own +0x24), C32C48 (0x9669D8: own
  +0x30/+0x34 and client random numbers, still drawn serially in the engine's order) and C32E28 (0x96BED6: on
  reaching the ground it runs an FXList - new systems and particles are the engine's, an evicted particle is
  forgotten by pxDel - and sets a system's +0x128). None writes a particle. All allowed; their code is in the hash.
- left out: model particles (~2%), types 7/8 containers (~2.5%), physics following the system or a drawable
  (~1.4%), systems following a particle (~0.4%).

**What the census found (v73 test, 18 min battle):** about 565 particles a frame, 1.2 ms a frame for their
update; 98% of class 0xBF7B70 particles use exactly the four classes above; 13% carry the drawable-attached module.
So in that test the gain is about 1 ms a frame; it grows with the number of particles (heavy spells). The v74
census (diagnostics) sorts every particle by pxpar's own test, and lists the system modules (+0x1AC..) with their
slots 1 / 4 / 5 - the next classes to verify and whitelist (`pxSysModOk`, the drift module).

## v77 additions, and what the next test must say
- **cbfind** (release): the top path of the logic samples was findNonConstCommandButton's list walk with a memcmp per
  node (0x406307 < 0x4065AA < 0x71D6B5). The answer is remembered per name bytes; valid while the list head, the bar
  and the match (`g_bdgMatches`) are unchanged; a clear is a new generation (no memset: a map's INI inserts thousands
  of buttons, each a new head). Command buttons are created only by INI loading (head insert 0x71D79F; overrides are
  separate objects), so the first match in list order cannot change in play.
- **taskwarm** (release): PerformRendering's pairwise light-environment compares (0x549430 > 0x53F3B0) were half of
  its samples, waiting for memory. A three-stage prefetch walk over the task array at its entry. `taskwarm:` (diag)
  gives its time with and without, in alternating 64-frame blocks: if there is no gain, set it off by default.
- **vmprobe** (diag): 14 000-19 000 page faults a second in calm play are not growth. NtAllocateVirtualMemory /
  NtFreeVirtualMemory are wrapped in ntdll (stub `mov eax, n` moved to a trampoline) and each commit / free is added
  to its caller module (stack walk past ntdll, kernel32, kernelbase, the CRT); working-set falls of 2 MB+ (Windows
  trimming) are counted every 30 ms. The `vmprobe:` line decides the fix: a module that commits and frees the same
  memory again and again (a cache of big blocks), or trims (a working-set floor).
- **Symbols** (diag): this DLL's functions are named in `framediag:` lines from `out\bfme2_accel.map` - our own share
  of the client step was 2.3 ms a frame in the v74 test (render queue recording and the diagnostics' own timers).

## v78 additions
- **strncpy for large sizes** (fastcrt): the render stage scope 0x517690 (one per batch in PerformRendering, so
  thousands a frame) copies its name with `strncpy(.., 0x100)`: 256 bytes written per call, mostly zero padding.
  game.dat's strncpy import now goes to fastStrncpy for sizes of 64 or more (SSE fill); shorter sizes still go to
  msvcr71 (its dword loop won there). Overlap including the terminator it reads goes to msvcr71.
- **Working-set floor** (aotr_guard.inc, `WSFLOOR_OFF`): a soft minimum of 1 GB (1.5 GB on 12 GB+ PCs) when the PC has
  6 GB+ and 1.5 GB free, so Windows does not trim the game's working set and fault it back in. vmprobe (diag) counts
  the trims that remain.
- Looked at and left: Player's has-any queries (0x7A19AB > 0x7A075A, Open-BFME-2's PlayerTeamPrototypeQueries: walk
  every team prototype's members; ~1.7% of the logic) - an exact memo would need every object change; MeshClass::
  Render copies the light environment into each mesh (Set_Lighting_Environment, 1.06 RVA 0x14BB20; the copy at mesh+0xCC), which is why
  the batch compare is deep - the read-ahead (taskwarm) is the safe answer.

## v79: small PCs (4 GB, two cores) - every part sizes itself
| Part | Rule |
|---|---|
| terrain-keep | off under 3.5 GB of memory; budget 48 MB under 6 GB, 112 MB under 10 GB, 160 MB above (the parked textures live in the game and DXVK keeps a copy); still drops everything at 2.9 GB used / 400 MB free |
| learned list (menu) | a third of the free memory, 512 MB at most; stops when under 1.2 GB is free |
| match preload / file read-ahead | (already) stops under 1.2 GB free; a third of the free memory, 1.5 GB at most |
| working-set floor | only with 6 GB+ and 1.5 GB free |
| pxpar | only with 3+ physical cores (on two, its one helper would share a core with the render worker and DXVK while the game thread waits) |
| helpers (terrain, texture jobs) | (already) by the number of cores |
- Diagnostics: taskwarm's timing keeps a stack of return addresses (game thread, 8 deep) instead of one, so a nested
  call can never return to the wrong place.

## v80: pxpar times itself on every PC
- Both ways (spread / engine alone) give the same particles, so the DLL times them in the player's own battles:
  64-frame blocks alternate; a frame's cost is the loop-start work (pick + spread) plus every particle container
  update, divided by the manager's particle count; only frames with 192+ particles count. After 900 counted frames
  of each kind it decides once: spreading stays if it costs at most 92% of the engine's way, else the engine does it
  for the rest of the session (`pxpar: trial - ...` in the log). A self-check that turns pxpar off also ends the
  trial (no more timing).
- taskwarm times itself the same way in the release build: 64-frame blocks with / without the read-ahead,
  PerformRendering's own time per frame (the return-address stack of v79); after 900 frames of each the report
  thread decides once (kept when <= 97% of the time without) and the timing stops. The diagnostics build keeps
  alternating all session for its 30 s line.
- v81: Object::findModule (0x68BDA5) is now memoised (aotr_fmfind.inc): the ObjectID offset was confirmed in 2.02 -
  GameLogic::registerObject puts `[obj+0x74]` into its id map (0x62BA6F, map at GameLogic+0xB4; findObjectByID is
  0x449681) - and the module array is written only by the constructor and the destructor.

## v84: the v83 test's freeze was ours (the glitch hunt's render-thread switch)
- 15 min, full graphics. Switches at play minutes 3, 6, 9, 12 went well; 0.8 s after the minute-15 switch to CORE:
  `crash: C0000005 at d3d9.dll+00EDB5` on a thread this DLL did not start (DXVK's own), then the game hung.
- Cause: ghTick (and, since v28, the dormant render-thread key in rtKeyThread) set `g_rtCoreMode = 1` at once, from
  its own thread, before rtApplyToggle had drained the queue. For that moment the game thread called DXVK directly
  while the worker still carried out queued calls - two threads in the device. The same race v33 removed from the
  freeze guard (texjob_test then caught an upload into a freed texture). Fix: both only set `g_rtWantOn`;
  rtApplyToggle (game thread, next Present) drains, then flips g_rtActive and g_rtCoreMode together. Nothing else
  writes g_rtCoreMode after start-up now (`grep "InterlockedExchange(&g_rtCoreMode"`: rtApplyToggle and the start).
- The hunt counts markers and minutes by the mode really in effect (g_rtActive), and stops switching once the freeze
  guard has stepped the render thread aside for good.
- Markers in v83: FULL 0 (8 min), CORE 1 (6 min) - too few to decide; the next test repeats it.

## Diagnostics build and how to measure

- `build.bat diag` defines `AOTR_DIAG`. The DLL then installs:
  - the panel (`aotr_overlay.inc`, F7, drawn into the game's back buffer);
  - the session report (`aotr_report.txt`, every 60 s);
  - the long-frame profiler (`aotr_loadprof.inc`), the whole-map query timer, and the client / flush / subsystem
    timers;
  - the right-Ctrl marker key, and the stack sampler: 50 samples a second in every game since v74 (`frame:` names
    the hot game.dat functions of the logic and the drawing every 30 s). Before v74 a statement written on the same
    line as an `#endif` in `aotr_frameprof.inc` was never compiled, so the sampler never ran in play at all (the
    v73 test's "0 samples a second"). Release: `FrameSampleHz` = 0, never sampled;
  - `aotr_fxprobe.inc`: particle update time, the census by pxpar's test, module classes, and the address space by
    kind (private / mapped / images) next to this DLL's own pools (parked ground textures, texture jobs, render
    thread buffer copies) - to tell the game's memory growth from ours.
- **Log lines to read** (diagnostics build): `perf:` every 5 s (fps, longest frame, page faults); `frame:` (logic
  vs client+drawing per frame, and its parts); `perf: stall` and `load:` (what a long frame was doing, as game.dat
  addresses); `rt:` (queue waits, freeze guard); one line per part every 30 s with its proof counts.
- **The learned list** (`aotr_learned.txt`, models and textures first opened during play): read into the file cache
  in the menu, newest first since v76 (the 512 MB budget used to go to the oldest names); trimmed to its newest
  256 KB when it nears 448 KB (it stopped learning at 512 KB before).
- `tools/gdnames.py` names game.dat functions by matching byte patterns against BFME2 1.06 from Open-BFME-2. Names
  file: `grep -rIhoE '\?[A-Za-z0-9_@?$]+ @0x[0-9A-Fa-f]{8}( [0-9]+B: .{0,100})?' $OB2/Code` into
  `/tmp/ob2names.json` ({rva: [name, note]}); `reverse/symbols.csv` is optional (v75 fix: the tool read the json's
  keys only and needed that csv). Most W3D functions are still unnamed there.
  The reference game.dat lives in a private repo, not here.
- **Multiplayer check without a second PC:** play with the DLL, save the replay, put `VANILLA` beside the DLL and
  watch the replay. It must end the same way.

## Working in this repo

- **No MSVC in a Linux container.** Check syntax with clang (it must print no errors, in both configurations):
  ```
  cd src
  clang --target=i686-w64-windows-gnu -fms-extensions -fdeclspec -fsyntax-only -w -Wundefined-internal -ferror-limit=0 -I../vendor/rpmalloc -DAOTR_PROD -DInterlockedExchange16=_InterlockedExchange16 aotr_accel.cpp
  # the same with -DAOTR_DIAG
  clang --target=i686-w64-windows-gnu -fms-extensions -fdeclspec -fsyntax-only -w aotr_start.cpp
  ```
  `-Wundefined-internal` must print nothing either: MSVC refuses a static function that is declared and called but
  never defined (C2129), which a plain syntax check lets through. A full clang build crashes on the inline
  assembly. The real build is MSVC (`build.bat`).
- **Generated files:** `aotr_rt_gen.inc` (from `gen_rt_hooks.py`), `aotr_texmem_gen.inc` (from
  `gen_texmem_stubs.py`), `gd_funcs.inc` (from `gen_game_funcs.py`). Edit the generator, not the output.
- **Big files:** `aotr_rt.inc` (~4000 lines), `aotr_rt_gen.inc` and `gd_funcs.inc`. Search them with grep; do not
  read them whole.
- **Version:** `AOTR_RELEASE` / `AOTR_BUILDNO` in `aotr_accel.cpp`. `AOTR_BUILDNO_GUARD` in `aotr_guard.inc` must
  equal the build number (`static_assert`).
- **Files the DLL keeps beside itself:**
  - `bfme2_accel.log` (one per start; the previous one is `bfme2_accel.prev.log`);
  - `filewarm.lst` (files opened in earlier sessions);
  - `aotr_learned.txt` (file names first opened in earlier battles: no paths, so it can ship with the package);
  - `aotr_guard.txt`; `aotr_power.txt` (the power settings to restore; written by the starter);
  - `aotr_status.txt` (the light's state for the starter's ring); `aotr_start.log` (the starter's own log);
    `aotr_path.txt` (where the AotR launcher is); `autostart_off` (the user switched autostart off).
